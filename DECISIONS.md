## 2026-08-31 — Task 13: trigger evals — purpose-built probe harness, de-conditioned descriptions, frozen holdout

- **Decision:** (a) Skill triggering is measured with a **purpose-built harness** (`tests/trigger_eval/run_trigger_eval.py`): each query runs in a headless `claude -p` session with the plugin via `--plugin-dir`, user/global settings dropped (`--setting-sources ""`), MCP disabled, and **every execution tool disallowed except `Skill`** — the first `Skill` tool_use in stream-json is the verdict and the process is killed the moment it appears (or after 8 assistant messages → "none"), so a probe costs one routing decision. Router model: **haiku**, the weakest available — the conservative stress test. Probes run from an empty temp cwd (no `runs/`, no project context) — the hard condition for downstream skills. (b) **Dev/holdout split**: `queries.yaml` (50 positives + 12 negatives) drives optimization; `holdout.yaml` (20 + 6) is never inspected until descriptions freeze. (c) The optimization itself: the baseline's dominant failure was **state-conditioned descriptions** — "a paper that ditto has ingested" made the router conclude "nothing is ingested here" and answer directly (19 of 21 misses were verdict "none"; ingest, with no such precondition, went 10/10). Fix: condition on the *topic* ("a paper in a ditto run"), add the routing instruction "do not skip because no run is visible in the current directory — the skill locates the run workspace from the manifest and reports cleanly if missing", broaden verb coverage, and name each skill's own invocation phrase ("ditto code" etc.). One overshoot (explain false-firing on a codebase question) fixed with an explicit scope guard. Ingest's description untouched. (d) One dev expectation corrected rather than optimized around: "how faithful is our implementation" accepts either `code` or `report` — both are correct routes.
- **Alternatives considered:** `claude plugin eval` (the natural vehicle — feature-gated off in CLI 2.1.201 behind statsig flag `tengu_walnut_spire`, default false; reverse-engineering the gate rejected); `skill-creator` tooling per the original task text (not installed on this machine); disallowing `Skill` too for cheaper probes (breaks detection — a disallowed tool is removed from the toolset entirely, so no attempt is ever visible); probing with a populated `runs/` workspace (strictly easier condition, weaker guarantee); 3 runs per query (3× cost; single-run plus targeted flakiness re-checks instead — both observed anomalies re-ran correct 3/3 and 5/5).
- **Why:** Evidence: dev positives 29/50 → 49–50/50, holdout 20/20, negatives 26/26 clean across both sets. The two-set split keeps the final number honest — the holdout was measured exactly once against frozen descriptions.
- **Consequences:** Descriptions now *promise* graceful no-run handling — the SKILL.md precondition steps (report + redirect to `ditto:ingest`) must keep honoring that. Trigger rate is measured on haiku only; stronger session models are inferred, not measured, to route at least as well. The harness is repo tooling: re-run it after any description change. If `plugin eval` un-gates, the query sets port to its `evals/` format.

## 2026-08-31 — Task 12: packaging — metadata-only plugin.json, self-listing marketplace, --plugin-dir cleanroom test

- **Decision:** (a) `plugin.json` stays **metadata-only** (name, version, description, author, homepage, repository, license, keywords) — Claude Code auto-discovers `skills/<name>/SKILL.md` and `agents/*.md` from their default locations, and our layout already matches the defaults, so explicit path registration would be dead configuration. (b) A **self-listing `.claude-plugin/marketplace.json`** (marketplace `ditto`, one plugin entry with `source: "."`) makes the GitHub repo directly installable via `/plugin marketplace add ArpitKadam/ditto` + `/plugin install ditto@ditto`; without it the repo would only be loadable session-scoped. (c) Torch stays **out of `pyproject.toml`**: the right build is hardware-dependent, so the README documents `uv pip install torch torchvision --index-url https://download.pytorch.org/whl/cu132` (CUDA) / plain CPU wheel as a manual step, per the standing project rule (never `uv add torch`). (d) The clean-install test uses `claude -p --plugin-dir <cold-copy>`: working tree copied to scratch minus `.git`/`.venv`/`runs/`/caches (a shipped-plugin simulation with no Python environment), headless session run from a separate empty project directory, ingesting **arXiv 1503.02531** (Hinton distillation — unseen by the pipeline, short, LaTeX e-print available). (e) The `claude plugin validate` CLAUDE.md-at-root warning is accepted: that file is the repo's development contract, not plugin-shipped context, and the runtime tolerates it.
- **Alternatives considered:** Explicit `skills`/`agents` path arrays in plugin.json (rejected: duplicates auto-discovery, one more thing to drift); shipping without marketplace.json (rejected: `--plugin-dir` is session-only, "installable" means durable); pinning a CPU torch in pyproject so `uv sync` gets everything (rejected: forces a 2+ GB wrong-build download on GPU users and contradicts the recorded install rule); testing against the live repo with its warm `.venv` (rejected: proves nothing about cold-path resolution — the venv and cache state are exactly what a fresh install lacks).
- **Why:** Auto-discovery is the documented default (code.claude.com/docs plugins reference, fetched this session); `claude plugin validate` passes both manifests; the cold copy + separate cwd is the closest scriptable approximation of "clean Claude Code environment" available on this machine.
- **Consequences:** Repo doubles as its own marketplace — releases should keep plugin.json and marketplace.json versions in agreement (`claude plugin tag` checks this). README owns the torch/first-run-downloads story; if the CUDA toolchain moves past cu132 the README command is the single place to update.

## 2026-08-31 — Task 11: report skill — no code, per-claim tested? column, trace-pass gate instead of a new agent

- **Decision:** (a) `ditto:report` ships as **SKILL.md + `templates/reproduction-report.md` only — no scripts, no pipeline additions, no tests**: report generation is a reading-and-writing task over `ir.yaml` + `impl/logs/` + `manifest.yaml`, and everything mechanical it needs (manifest marking) already exists in `pipeline/workspace.py`. (b) The claims table carries **one row per `evaluation.headline_results` entry with a per-row `tested?` column** — `not attempted (needs T3)` / `directional analogue (T2)` / etc. Untested claims are never dropped and never juxtaposed with non-comparable local numbers; below T3 the mostly-`not attempted` table *is* the honest deliverable. (c) Two governing rules written into the template: **no number without a source** (claimed numbers cite their IR `src`, achieved numbers cite the `impl/logs/` file they were read from) and **never fake a comparison**. (d) Fixed section order: verdict, tier scorecard (including `*_failed_*` negative evidence per tiers.md), claimed-vs-achieved, assumptions+unknowns (with how each unknown was resolved, cross-referenced from deviations), full deviations log, unknowns-that-mattered (risk-ranked subset, benign tier-scope cuts explicitly separated), compute (evidence headers only, contrasted with `training.hardware`), **path to T3** (the section that must answer "what would it take" concretely), reviewer gates. (e) **No `report-reviewer` agent added** — the target layout defines exactly three agents; verification is a trace pass (step 3 of the skill: re-locate every number in its cited source) plus the template self-check. This session ran fresh-context trace reviews via general reviewer subagents as the acceptance check; the skill itself stays self-contained.
- **Alternatives considered:** A `report-reviewer` agent file (rejected: fourth agent not in the contract layout, and the trace pass is a mechanical checklist a fresh agent adds little to — unlike the impl/viz reviewers, which judge semantics); comparing T2's validation loss against the paper's BLEU rows in one table (rejected: fakes comparability — the directional analogue gets its own honestly-labeled row and a prose caveat); a script that auto-generates the claims/deviations tables from the IR (rejected on the ladder: the abridging judgment is the work, YAML-to-table plumbing saves nothing); reports for papers 1–2 only per the acceptance floor (all three written: the data was in hand and Grokking — the deliberately underspecified paper — is the template's stress test for the assumptions machinery).
- **Why:** The report is the payoff artifact of the whole pipeline; its authority comes entirely from traceability, so the design puts every enforcement point on sourcing and none on prose. Ponytail rung 1 for code: nothing here needs to exist as a program.
- **Consequences:** `templates/` directory now exists (first file). Reports go stale if tiers advance — re-running `ditto:report` after new evidence is the intended refresh, cheap because everything regenerates from workspace state. Claims tables at T1/T2 are dominated by `not attempted` rows by design; that is a feature reviewers must not "fix".

## 2026-08-31 — Task 10: visualize skill — matplotlib-only, IR-status architecture diagram, dump-convention attention viz

- **Decision:** (a) All three viz scripts use **matplotlib only** — no `graphviz` (needs a system binary the dependency ladder forbids for a box diagram matplotlib draws fine) and no `torchview` (needs an importable model instance; each run's `impl/` is a different package, while `ir.yaml` is the one shared contract). (b) `architecture_viz.py` renders the IR's `architecture.layers` list as a vertical flow diagram **color-coded by confidence status** (stated/inferred/assumed/unknown) with the status printed as text in every box — the diagram shows what the IR actually knows, which no model-instance tracer can. Palette `#0072B2/#009E73/#E69F00/#D55E00` validated with the dataviz six-checks script (CVD worst-pair ΔE 18.3 PASS; the amber contrast WARN is relieved by the in-box status text). (c) `training_viz.py` discovers `impl/logs/t1_overfit.csv` and `impl/logs/t2_trend/*.csv`, parses their `#`-comment provenance headers, and re-renders presentation-grade curves (log-y for multi-decade loss, pass-bar line, arm colors fixed by entity); it plots **only numbers present in the CSVs** — provenance line quoted from the header. (d) `attention_viz.py` renders heatmaps from tensors the impl dumps to `impl/logs/attention/*.npz` (convention: arrays named `layer{i}_head{j}` or a single `attn`, optional `tokens` labels) — the viz layer cannot generically instantiate arbitrary impl models, so the impl dumps, the script renders. The skill decides **from the IR** whether attention viz is warranted (method operates on/modifies attention) and requires a dump or checkpoint to exist; absent that, it records why it skipped. (e) `viz-reviewer` agent is optional-lightweight: fresh-context, checks each plot against the numbers/files it claims to render. (f) Outputs land in `runs/<slug>/viz/` (Contract 1); every plot regenerable by re-running its script against workspace state alone.
- **Alternatives considered:** graphviz/torchview per the original locked-decision stack note (both rejected on the ladder — matplotlib is already installed and the IR-status diagram is *more* honest than a traced graph); attention viz that retrains LoRA to get a checkpoint (real but outside Task 10's acceptance, and Task 9 deliberately persisted logs-only evidence); reusing the train.py-produced `t1_overfit.png` as the viz output (tier evidence and presentation viz have different jobs; the viz must be regenerable by the viz script).
- **Why:** Ponytail ladder (rungs 2/5: matplotlib already here) plus the IR-first principle — the architecture diagram's job in a *reproduction* tool is to show claim confidence, not just topology.
- **Consequences:** No new dependencies. Papers whose impl never dumps attention get no attention viz — recorded, not fabricated. `plotting-patterns.md` encodes the dataviz rules (one axis, recessive grid, fixed entity colors, direct labels, provenance caption) for all future plot code.

## 2026-08-31 — Task 9: end-to-end runs — transformers dep, T2 design for LoRA, T1 designs, GPU scheduling

- **Decision:** (a) Add `transformers` (managed dep) for the LoRA T2 arm — distilgpt2 as the small pretrained model; `datasets` NOT added: the E2E NLG corpus is fetched directly from the original GitHub CSV release and subset. (b) **LoRA T2 metric = validation loss**, which is a paper metric (the rank-ablation table reports E2E validation loss), arms = frozen distilgpt2 baseline vs LoRA-adapted (Wq,Wv, r=4, α=32 per IR); directional pass = LoRA validation loss clearly below frozen baseline after minutes-scale training. BLEU deliberately not computed (would add a metrics dep for a directional check the loss already gives). (c) **DDPM T1** = overfit a fixed (x₀, t, ε) triple — with resampled noise the L_simple expectation has a nonzero floor, so the honest gradient-flow proof fixes the regression target; justification recorded in the evidence header. MNIST 28×28 stands in for CIFAR-10 at T1 scale (deviation entry); sampling-grid bonus only if time permits. (d) **Grokking T1** = single-batch answer-token cross-entropy overfit on the division-mod-97 table; the IR's supplemental unknowns (embedding kind, weight tying, init) get RESOLVED entries. (e) GPU scheduling on the 4GB RTX 3050: DDPM + Grokking executors run in parallel (both tiny), LoRA runs alone afterward with the GPU to itself. (f) Executors run SKILL.md steps 0–5 and stop; the implementation-reviewer gate and manifest marking happen from the main session (subagents cannot spawn subagents), with fix cycles routed back to the same executor via message.
- **Alternatives considered:** `datasets` library (heavy dep for one CSV); BLEU via sacrebleu (extra dep, weaker signal than val loss for a directional check); DDPM T1 with resampled noise and a "loss decreased" bar (proves less and reads as evidence-fudging); running all three executors concurrently on one 4GB GPU (OOM flakiness risk for zero schedule gain).
- **Why:** Each choice is the smallest honest version of its tier per Contract 4 and tiers.md; validation loss as the T2 metric keeps the comparison inside what the paper itself reports.
- **Consequences:** `transformers` in pyproject (pulls numpy, silencing torch's numpy warning); model/dataset downloads happen at run time into the HF cache / run workspace. Task 12's README must note the torch-install command plus first-run downloads.

## 2026-08-31 — Task 8: implementation-reviewer — check classes, severity lines, tier-gated wiring

- **Decision:** (a) `agents/implementation-reviewer.md` is fresh-context and read-only (Read/Grep/Glob), input = a run directory; it reads `ir.yaml` + the full `impl/` tree (runs/ is gitignored, so "the diff" is the whole implementation) and has **no implementer context by design**. (b) Four check classes: **equation-vs-code** (each IR equation with `implements` diffed line-by-line against its code site), **config-vs-status** (every `config_paper.yaml` value traced to IR status; an `assumed`/`unknown`-derived value presented without a RESOLVED marker + deviation entry = finding), **unlogged deviations** (code departing from IR statements with no `implementation_notes.deviations` entry), **test honesty** (tests that inspect without asserting, or assert tautologies). (c) Output = one severity-tagged line per finding, `path:line: [HIGH|MED|LOW|INFO] problem. fix.` — HIGH = wrong math/silent assumption-as-fact; MED = unlogged deviation/missing assertion; LOW/INFO = traceability gaps. (d) Review saved to `impl/logs/review_<tier>.md`; wired into `skills/code/SKILL.md` as a **mandatory step between tier evidence and manifest marking** — `tier_reached` is only recorded after HIGH/MED findings are fixed or explicitly accepted by the user. (e) Seeded-bug acceptance test: LoRA's T0 impl has no loss function, so the seeded "wrong sign in loss" becomes a sign flip in the eq3 forward (`h = W0x − BAx·α/r`) — the equation-implementing site that exists at T0 — seeded in a scratch copy of the workspace, never in the real run.
- **Alternatives considered:** Reviewer with implementer context (defeats the bias-check purpose); git-diff-scoped review (impl/ is untracked; whole-tree read is the honest scope at this size); blocking on LOW findings (turns the gate into noise); seeding the bug in the real workspace and reverting (runs/ has no git safety net — a scratch copy risks nothing).
- **Why:** Fresh context is the value: the reviewer argues with the IR, not with the implementer's reasoning. The four classes cover the reproduction-specific failure modes generic reviewers miss.
- **Consequences:** `ditto:code` gains a hard gate; Task 9's end-to-end runs must budget for review+fix cycles. Contract 4 evidence set now includes `review_<tier>.md`.

## 2026-08-31 — Task 6: mirror rule widened — supplemental sub-field unknowns/assumptions

- **Decision:** `implementation_notes.unknowns`/`assumptions` may now contain, in addition to the auto-derived whole-leaf entries, **supplemental entries** whose field path extends a tracked status leaf with a dot suffix (e.g. `training.init.sigma_A`, `training.optimizer.adam_betas_eps`, `architecture.layers[1].kind`). Semantics: the leaf's own status stays honest (a field can be `stated` overall while one sub-detail is unknown), and the sub-detail gets a first-class ledger entry so downstream skills (code's deviations, report's assumptions table) see it. `ir_build --derive` preserves supplemental entries instead of clobbering them; `ir_validate` accepts an entry iff it is either an exact mirror of a tagged leaf or a valid supplemental (existing tracked-leaf prefix + non-empty suffix) — anything else is a finding. No IR fields added or renamed; this widens the mirror rule only.
- **Alternatives considered:** Sub-field `{value, status, src}` everywhere (schema explosion; rejected at the freeze and still wrong); leaving sub-detail gaps as prose inside `value` (what we had — Task 6's explain runs showed it hides implementer-facing unknowns from the structured ledger on 2 of 3 papers); demoting a whole leaf to `unknown` when one sub-detail is missing (destroys real information — LoRA's init *scheme* is fully stated, only σ is not).
- **Why:** Evidence from the explain quality gate: LoRA surfaced three prose-buried unknowns (σ of A's Gaussian init, Adam β₁/β₂/ε, GPU count) and DDPM one (σ_t² = β_t vs β̃_t for the headline runs — needed by Algorithm 2, never committed to in the paper). Explain doubles as IR validation by design; the gaps it logs must be actionable into the ledger or the ledger lies to the report skill.
- **Consequences:** Schema v0 remains frozen shape-wise; this is a validator/derive semantics change (post-freeze change, hence this entry). The three run IRs gain supplemental unknowns; ingest SKILL.md fill rules and the ir.yaml header comment document the convention.

## 2026-08-31 — Task 6: explain skill — self-contained math, in-document gap log, on-demand rasterization

- **Decision:** (a) Equations in `explain.md` must be **self-contained standard LaTeX**: author-defined macros (`\bmu`, `\defeq`, `\Eb`, `\cZ`, …) are expanded using their `\newcommand` definitions from the `source/` preamble before rendering, wrapped in `$$…$$`/`$…$` so Markdown previews typeset them. The IR and `ir_audit.md` stay verbatim-faithful — readability transforms happen only in reader-facing documents (prompted by the user's rendering question after Task 5). (b) IR deficiencies discovered while explaining (a `src` pointer that had to be followed into `source/` because the IR was too thin) are logged in an **"IR gaps" section at the bottom of `explain.md` itself** — self-contained in the run workspace, no new file, honest to the reader. (c) Architecture diagrams that exist only as vector PDFs are rasterized on demand by a new `pipeline/rasterize.py` (PyMuPDF, 150 dpi, PNG written next to the original) so `explain.md` can embed a working `![]()` image — this closes the Task 3 "rasterize on demand" deferral for the explain path. (d) Template lives at `skills/explain/references/explanation-template.md`; structure per TASK.md: problem → intuition → method walkthrough keyed to equations (each rendered *and* given meaning) → architecture with embedded diagram → training recipe table with per-field confidence surfaced → what's unknown/assumed. (e) Explain marks `manifest stages.explain` done via `workspace mark`.
- **Alternatives considered:** Rendering with a KaTeX macros preamble instead of expansion (couples explain.md to a specific renderer config; expansion produces universally renderable LaTeX); a separate `explain_gaps.md` file (extra Contract 1 surface for a section that belongs with its document); embedding PDFs directly in Markdown (does not render in any mainstream preview); converting all figures to PNG at extract time (rasterizes many figures nobody embeds; on-demand is one file).
- **Why:** The Task 5 rendering complaint showed exactly where the verbatim/readable boundary must sit. Everything else follows the ponytail ladder.
- **Consequences:** `figures/` may contain both `figN.pdf` and a derived `figN.png`; `figures.yaml` keeps pointing at the original (provenance), explain.md embeds the PNG. Downstream skills needing raster figures reuse `pipeline/rasterize.py`.

## 2026-08-31 — Task 5: ingest skill design — resumable workflow, audit report in-workspace, mark_stage helper

- **Decision:** (a) `skills/ingest/SKILL.md` is a **resumable** workflow: every step first reads `manifest.yaml` and skips stages already `done` — re-invoking ingest on an existing run continues where it stopped (filesystem-is-state applied to the skill itself). (b) Pipeline invocation form in SKILL.md: `uv run --directory "${CLAUDE_PLUGIN_ROOT}" python -m pipeline.<module> …` with absolute `--runs-dir`/run-dir arguments, so the module resolves from the plugin root while workspaces live in the user's project; full clean-install verification deferred to Task 12. (c) Manifest updates go through a new `workspace.mark_stage(run_dir, stage, **fields)` + CLI (`python -m pipeline.workspace mark <run> <stage> key=value …`, values parsed as YAML scalars) — every downstream skill needs the same mechanical update; skills never hand-edit manifest YAML. (d) The auditor's report is saved to `runs/<slug>/ir_audit.md` (Contract 1 addition). (e) `agents/ir-auditor.md` is a read-only fresh-context agent (Read/Grep/Glob only): samples 10 `stated`/`inferred` claims (all, if fewer) spread across IR sections incl. equations and headline results, resolves each `src` against `paper.md`/`source/`, verdicts SUPPORTED / UNSUPPORTED / CONTRADICTED; any UNSUPPORTED or CONTRADICTED = fabrication, gate fails. Until the plugin is installed (Task 12), the skill spawns a general subagent carrying the same instructions.
- **Alternatives considered:** Skill always restarts from fetch (wastes network and tokens, contradicts filesystem-is-state); hand-editing manifest.yaml from the skill (drift-prone, untested); auditor with Write access saving its own report (wider tool surface for no gain — the ingest workflow saves the returned report); auditing every IR claim (cost scales with IR size; 10 sampled claims with zero-tolerance is the contract's bar).
- **Why:** Resume semantics make the skill safe to re-run after any interruption — the property the whole architecture promises. `mark_stage` keeps Contract 3 writes in tested code.
- **Consequences:** Contract 1 gains `ir_audit.md`; ARCHITECTURE.md updated. Auditor tool surface stays read-only. Task 12 must verify `${CLAUDE_PLUGIN_ROOT}` invocation and registered-agent spawning in a clean install.

## 2026-08-31 — Task 4: IR skeleton in code; all-unknown init; mechanical mirror via `--derive`

- **Decision:** (a) `ir_build.py` generates the IR skeleton in code — no `templates/ir-skeleton.yaml` file — following the `workspace.new_manifest` precedent; guidance for filling (status legend, src format, validator rules) lives in a static YAML header comment prepended to the dump. (b) Every status-carrying leaf initializes to `status: unknown` and `implementation_notes.unknowns` is pre-derived, so a freshly built or partially filled IR validates clean by construction. (c) The `{value, status, src}` convention applies to *value-bearing* leaves only: `problem.statement/motivation`, `method.summary`, the ten `training.*` fields, and `architecture.layers[]` items. `method.components[]` and `mathematics.equations[]` keep their contract shapes (src required, no status); `paper.official_repo` is metadata (shape-checked, excluded from the mirror). (d) The assumptions/unknowns mirror is resynced mechanically by `python -m pipeline.ir_build <run> --derive` (preserves hand-written `basis` per field); `ir_validate.py` stays pure read-only — it never rewrites, and manifest updates are left to the ingest skill (Task 5). (e) "Parseable LaTeX" for equations = non-empty, balanced braces (escape-aware), and matched `\begin{X}`/`\end{X}` pairs — no LaTeX-parser dependency. (f) `ir.yaml` gains a top-level `figures:` inventory (`{id, file, caption}` from `figures/figures.yaml`, glob fallback for the PDF path) so the code/visualize skills see figures without re-reading the workspace; schema addition is pre-freeze (freeze is after Task 5).
- **Alternatives considered:** A `templates/ir-skeleton.yaml` file (second source of truth; pre-fill needs code anyway — the manifest already set the code-only precedent); initializing statuses empty (a partial IR could never validate clean, violating the acceptance criterion); requiring status on components/equations (contract 2 shows their shapes without it; equations are verbatim-from-paper by definition); making the validator auto-fix the mirror (validator must be a pure check so exit codes are trustworthy in the skill loop); full LaTeX parsing for equations (a dependency for what a 15-line balance check catches — truncation and mangling, the real failure modes).
- **Why:** Ponytail ladder + the Task 4 acceptance criteria: validator catches each seeded violation class, a hand-filled partial IR validates clean, and the contract's "auto-derived" notes actually are auto-derived.
- **Consequences:** `--derive` rewrites `ir.yaml`, dropping any inline comments Claude added (the static header survives; data belongs in fields). The status-leaf set is defined once (`ir_build.status_fields`) and imported by the validator, so schema drift between build and validate is impossible. Revisit the leaf set and the `figures:` section at the Task 5 quality gate.

## 2026-08-31 — Task 3: extraction is LaTeX-preserving, not detex'd

- **Decision:** `paper.md` keeps the LaTeX document body verbatim — comments and preamble stripped, but math environments, tables, and inline math left as LaTeX source. No conversion to prose/plain text. `\includegraphics` targets are rewritten to stable `figures/figN.<ext>` names (original extension kept, no rasterization), the asset copied, and provenance + a best-effort caption recorded in `figures/figures.yaml`. Parsing is regex + a depth-aware brace matcher, no LaTeX-parser dependency. PDF path uses the already-locked PyMuPDF; HTML path uses stdlib `html.parser`.
- **Alternatives considered:** (a) `pylatexenc`/full detex to prose — lossy for equations and adds a dep; the IR is an index that zooms back into `source/`, so fidelity beats readability here. (b) `pandoc` — heavy external binary. (c) Rasterizing PDF/EPS figures to PNG now — needs a renderer per figure and is only required when a skill must *view* a diagram (Task 5/7), so deferred. (d) `beautifulsoup4` for HTML — a dep the stdlib parser makes unnecessary for the fallback path.
- **Why:** Ponytail ladder — the acceptance criteria (equations present as valid LaTeX, figures copied, tables survive as LaTeX) are met by a preserve-and-rewrite pass without a parser dependency. Verified on all three papers.
- **Consequences:** `figures/figN` keeps mixed extensions (LoRA figures are `.pdf`). A skill that needs a raster diagram must rasterize on demand — tracked as a Task 5/7 follow-up. Caption cleanup strips inline-math macros (`\times` → gone) in the *convenience* `caption` field only; the faithful caption remains verbatim in `paper.md`. Same trust-boundary containment as Task 2 applies: `_within()` blocks `../` asset traversal out of `source/`.

## 2026-08-31 — Task 2: fetch implementation choices

- **Decision:** (a) Use stdlib `urllib` for the three arXiv endpoints (e-print, export API, /html) instead of the `arxiv` package or `requests`. (b) Flatten multi-file LaTeX with a small in-repo Python `\input`/`\include` resolver instead of `latexpand`. (c) Slug = bare arXiv id with `/` → `-` (old-style ids), or sanitized filename stem for local/PDF-URL inputs. (d) Network tests carry a `network` pytest marker and are deselected by default (`addopts = -m 'not network'`); run explicitly with `-m network`.
- **Alternatives considered:** `arxiv` PyPI package (adds a dep + transitive `feedparser`/`requests` for three simple GETs); `requests` (a dep for what `urllib` does); `latexpand` (Perl — not present on Windows, adds a non-Python runtime dep); running network tests by default (flaky, slow, rate-limited in CI).
- **Why:** Ponytail ladder — stdlib covers HTTP and gzip/tar; a ~20-line flattener covers the arXiv multi-file case without a Perl dependency. Marked network tests keep `uv run pytest` fast and offline-deterministic while still exercising live fetch on demand.
- **Consequences:** `pipeline/fetch.py` depends only on `PyYAML` beyond stdlib. LaTeX flattening resolves paths against the compilation-root dir (TeX semantics) and is containment-checked against untrusted e-print content. Revisit `latexpand` only if a real paper's `\input` structure defeats the simple resolver.

## 2026-08-31 — Task 2: hardening untrusted downloaded content (security)

- **Decision:** Treat downloaded e-print tarballs, arXiv API XML, and rendered HTML as untrusted at the trust boundary. Concretely: tar unpack uses `extractall(filter="data")` (PEP 706) — which sets the real floor `requires-python = ">=3.11.5"`; LaTeX `\input`/`\include` targets are rejected unless they resolve inside the source tree; XML is refused if it contains a DTD (`<!DOCTYPE`/`<!ENTITY`) before parsing, guarding XXE/billion-laughs; HTML `<img>` assets are downloaded only over `http(s)` from an `arxiv.org` host, blocking `file://` local reads and internal-host SSRF.
- **Alternatives considered:** Trusting arXiv content implicitly (arXiv is author-uploaded — a malicious paper is a realistic threat); `defusedxml` (an added dep; the DTD-reject guard covers the two relevant attacks for this single well-formed feed); leaving `requires-python = ">=3.11"` (allows 3.11.0–3.11.4 where the `filter` kwarg raises `TypeError`, silently disabling the tar guard).
- **Why:** Found by `security-review` (path traversal, HIGH; `file://`/SSRF, MED) and `cavecrew-reviewer` (the 3.11.5 `filter` floor). Each is a real exploit path triggered by merely fetching a crafted arXiv id; each fix is a few lines with a regression test.
- **Consequences:** Minimum Python is 3.11.5. Any future fetch path added must re-apply the boundary checks. Revisit `defusedxml` if the pipeline ever parses XML from more sources.

## 2026-08-31 — Source priority: arXiv e-print LaTeX → arXiv HTML → PDF hybrid

- **Decision:** `arxiv.org/e-print/{id}` tarball is the primary source; `arxiv.org/html/{id}` is the fallback; PDF is last resort (PyMuPDF text extraction + rendered page images at ~150 dpi).
- **Alternatives considered:** PDF-first (simplest single path); HTML-first (clean markup).
- **Why:** The e-print tarball is lossless for equations, pseudocode, tables, and figure assets. HTML keeps clean markup + images but is not available for all papers. PDF is token-hungry and lossy.
- **Consequences:** `pipeline/fetch.py` implements the three-way fallback; extraction (Task 3) needs a code path per source kind. Revisit if arXiv changes e-print availability.

## 2026-08-31 — Shared Paper IR with per-field provenance

- **Decision:** One `ir.yaml` per run with per-field `{value, status, src}`; status ∈ `stated | inferred | assumed | unknown`; `src` is a section/equation/page/figure pointer. The IR is an **index, not a replacement** — downstream skills zoom back into `source/` via `src` pointers when ambiguous.
- **Alternatives considered:** Free-form notes per skill (no machine-checkable provenance); IR as full replacement for the source (loses detail, invites fabrication).
- **Why:** Per-field status makes assumptions and unknowns first-class and mechanically auditable; `src` pointers make every claim checkable against the source.
- **Consequences:** `ir_validate.py` enforces status coverage and provenance; `implementation_notes.assumptions/unknowns` are derived from statuses. Schema freezes after Task 5.

## 2026-08-31 — Filesystem is the state

- **Decision:** All inter-skill state lives in the run workspace (`runs/<paper-slug>/`) plus `manifest.yaml`; never in conversation memory.
- **Alternatives considered:** Conversation-carried state (dies with the session); a database (overkill for per-paper artifacts).
- **Why:** Any skill invoked in a fresh session reads the manifest and picks up exactly where the last one stopped.
- **Consequences:** Contracts 1 and 3 (workspace layout, manifest schema) are the interface between skills; changes to either require a decision entry.

## 2026-08-31 — Verification tiers T0–T3 for ditto:code

- **Decision:** Four tiers — T0 code runs, T1 learns at all (single-batch overfit), T2 trend reproduces (scaled-down), T3 numbers reproduce. Target tier declared up front; two configs always produced (`config_paper.yaml` faithful, `config_small.yaml` runs in minutes). Default target T1, T2 where compute permits, T3 opt-in only.
- **Alternatives considered:** Binary "reproduced / not reproduced" (hides how far the reproduction actually got); always targeting paper-scale numbers (infeasible on session compute).
- **Why:** Tiers make the honesty of a reproduction claim explicit and cheap to verify incrementally.
- **Consequences:** Every tier claim requires evidence in `impl/logs/`; the manifest records `tier_target` vs `tier_reached`.

## 2026-08-31 — Official repo check is step zero of ditto:code

- **Decision:** If a reference implementation exists, the IR links it and validation diffs against it before any implementation work.
- **Alternatives considered:** Clean-room implementation always (wastes the strongest available ground truth).
- **Why:** An official repo is the highest-fidelity oracle for ambiguous paper details.
- **Consequences:** `ditto:ingest` records `official_repo` in the IR; `ditto:code` starts with the check.

## 2026-08-31 — Packaging: Claude Code plugin with thin skills over pipeline/

- **Decision:** Package as a Claude Code plugin: skills + reviewer subagents + shared `pipeline/` Python package. Skills stay thin; deterministic work lives in `pipeline/`, referenced via `${CLAUDE_PLUGIN_ROOT}`.
- **Alternatives considered:** Standalone CLI (loses skill triggering and subagent integration); logic embedded in SKILL.md prose (non-testable, drifts).
- **Why:** Deterministic work belongs in tested Python; judgment work belongs in skills. The plugin boundary keeps both installable as one unit.
- **Consequences:** Every skill invokes `pipeline/` rather than reimplementing; `${CLAUDE_PLUGIN_ROOT}` paths must resolve in a clean install (Task 12).

## 2026-08-31 — Stack: Python via uv, minimal core deps

- **Decision:** Python managed with `uv`.
